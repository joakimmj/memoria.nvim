==============================================================================
1. INTRODUCTION                                     *memoria-introduction*

memoria.nvim keeps notes as plain markdown. A brain is a folder of notes; an
engram is one note in it. Files stay readable without the plugin.

                                                          *memoria-vocabulary*
Commands and functions are named by what they do to their noun, one meaning
per verb:

    Register    record something that exists outside memoria: a brain
                folder. Its inverse is Deregister.
    Create      make something new: an engram, a concept
    Attach      put a relation on the current engram: a synapse, a concept
    Edit        change what an existing thing carries: a concept's meta

Nothing is mapped by default.

==============================================================================
2. REQUIREMENTS                                     *memoria-requirements*

Neovim 0.10 or later, and md-drafting.nvim with its `api` table.
`setup()` checks for it and stops with an error when it is missing.

==============================================================================
3. CONFIGURATION                                          *memoria-config*

Three tiers, later over earlier: built-in defaults, `setup()`, and the
brain's own `.mia_dna.json`. Maps merge by key; lists replace wholesale.

                                                           *memoria-config-null*
A missing key follows the tier above. `null` in JSON, or `vim.NIL` in
`setup()`, removes it instead:

- an entry in `synapses` or `concepts` stays removed, e.g.
  `{ "synapses": { "up": null } }` gives the brain no `up` field;
- any other setting goes back to its built-in default, skipping the value
  from `setup()`.
Every value below is the default: >lua

    require("memoria").setup({
      -- Create the :Mia* user commands.
      add_commands = true,

      engrams = {
        -- Tokens: YYYY, YY, MM, DD, HH, mm, ss.
        date_format = "YYYYMMDD",
        filename = {
          -- "date", "concept" or "none".
          prefix = "date",
          separator = "_",
        },
        -- Prose under the generated header. %cursor% marks where typing
        -- starts; %title% and %date% are expanded.
        content_template = "# %title%\n\n%cursor%",
        -- Checkbox markers the atlas indexes, by state. Replaces the
        -- default rather than adding to it.
        task_markers = {
          not_done = { "[ ]" },
          done = { "[x]", "[X]" },
        },
      },

      -- Engram fields go in the SYNAPSES block, concept fields in
      -- frontmatter. Both are written sorted by name.
      synapses = {
        -- target: "engram" or "concept". show_empty writes the field
        -- even with no values. inverse: the engram field kept in sync on
        -- the other side. list = false: one value, replaced on add, and
        -- written as one rather than as a list of one.
        -- concept_type: the one concept type a concept field takes, and
        -- refuses the rest. Required on every concept field.
        up = { target = "engram", inverse = "down", list = true, show_empty = true },
        down = { target = "engram", inverse = "up", list = true, show_empty = true },
        tags = { target = "concept", concept_type = "tag", list = true },
      },

      -- The concept types this brain has, and what each is asked for when
      -- its meta is filled in, see |memoria-concepts|. A concept's type is
      -- one of these, or one the registry already uses.
      concepts = {
        tag = { fields = { "description" } },
      },
    })
<
                                                      *memoria-mia_dna.json*
A brain's `.mia_dna.json` holds only what differs, with the same keys: >json

    { "engrams": { "filename": { "prefix": "none" } } }
<
|:MiaBrainConfig| opens the file, writing `{}` first when the brain has none.
Keys left out follow `setup()` and the defaults, so an override keeps working
when those change — write only what this brain needs. It cannot set
`add_commands`. JSON has no comments. An unreadable or invalid file is
reported and skipped.

==============================================================================
4. BRAINS                                                 *memoria-brains*

Brains are registered per machine in `stdpath("data")/memoria/brains.json`,
with absolute locations. Deregistering never touches files.

The active brain lives for the session only. When a brain is not named, it
is resolved in this order:

    1. the brain holding the current buffer's file
    2. the active brain
    3. the only registered brain, when there is exactly one
    4. a picker over registered brains

So the active brain is not always the one acted on. |:MiaBrainList| marks
both: `>` the brain holding the current buffer, which wins, and `*` the active
one. Prompts name their brain, e.g. >

    (work) Engram title:
<
A brain that *is* named must exist: an unknown name is an error, never the
picker. Steps 3 and 4 are why the CLI (|memoria-cli|) needs `--brain` only
when more than one brain is registered.

The concept commands take the brain too, and ask for the concept inside it: a
concept name means nothing until its brain is known.

==============================================================================
5. ENGRAMS                                               *memoria-engrams*

|:MiaEngramCreate| asks for a title. The title is written as typed into
%title%; the filename uses its slug: >

    Note about Java
    20260801_note_about_java.md      prefix = "date"
    java_note_about_java.md          prefix = "concept", java picked
    note_about_java.md               prefix = "none"
<
With `prefix = "concept"`, |:MiaEngramCreate| picks the concept before it asks
for the title (|memoria-concepts-pick|). The concept is also written into the
field taking its type, so a prefix is never only cosmetic: a `java_` file
nothing tags `java` would be visible in a listing and invisible to everything
that searches. With more than one field taking that type the field is picked
too; with none, there is nowhere to write it and the engram is refused.
The slug is lowercased, whitespace becomes `filename.separator`, and
characters no filesystem allows (/ \ : * ? " < > |) are dropped. When the file
already exists, or nothing usable is left, |:MiaEngramCreate| asks again with
the title filled in and the reason in the prompt.

The file gets a generated header, then the content template: >markdown

    ---
    tags: []
    ---
    <!-- SYNAPSES -->
    - **down:**
    - **up:**
    ***
    <!-- /SYNAPSES -->

    # Note about Java
<
The frontmatter is left out when no `synapses` field has target "concept",
and the SYNAPSES block when none would show a line. A brain with every field
removed (|memoria-config-null|) gets plain markdown. A blank line separates
the header from the template, and is left out with the header.

The buffer opens with the cursor at %cursor%.

==============================================================================
6. SYNAPSES                                             *memoria-synapses*

|:MiaSynapseAttach| links the current engram to another through an engram
field, and writes the field's `inverse` on the other one: >markdown

    <!-- SYNAPSES -->
    - **down:**
    - **up:** [20260801_project-x](20260801_project-x.md)
    ***
    <!-- /SYNAPSES -->
<
Link text is the filename without `.md`. Adding a link that is already there
changes nothing, so adding it again repairs a synapse with only one side. A
field with `list = false` gives up its old value, and that engram loses its
inverse back. A field without an `inverse` is written on one side only.

A field line the config does not name, e.g. one added by hand, is kept.
Frontmatter that cannot be read stops the write, and neither file changes.
An engram open in a buffer is written through the buffer and saved.

==============================================================================
7. CONCEPTS                                             *memoria-concepts*

A concept is something an engram names without being a file of its own: a
person, a tag, a topic. Concept fields (`tags`, and any other with target
"concept") hold concept names in frontmatter; the brain's registry says what
each name is.

                                                   *memoria-mia_concepts.json*
The registry is `mia_concepts.json` in the brain folder: visible and meant to
be read and edited by hand, one key per line, keyed by name: >json

    {
      "Alice Smith": {
        "aliases": [
          "Alice"
        ],
        "meta": {
          "email": "alice@example.com"
        },
        "type": "person"
      }
    }
<
`type` is one the brain has: a type given a schema under `concepts` in
|memoria-config|, or one its registry already uses. Nothing else is offered
or accepted, so `room` and `rooms` cannot become two types by a typo; a type
the brain has never seen starts with a schema in the config. `aliases` are
other names that resolve to the same concept. `note` is free text. `meta` is
free-form, and the type's schema decides which keys are asked for. Keyed by
name, a registry cannot hold the same concept twice.

                                                      *memoria-concepts-types*
Every concept field declares the one `concept_type` it takes, and refuses a
concept of any other. `tags` takes tags; to put a `room` on an engram, the
brain configures a field for rooms: >json

    { "concepts": { "room": { "fields": ["floor"] } },
      "synapses": {
        "rooms": { "target": "concept", "concept_type": "room" }
      } }
<
A concept field without a `concept_type` takes nothing, and is reported as the
config mistake it is rather than read as a field taking anything.

A field is written the shape it is declared: a list by default, and with
`list = false` the value itself, or the bare key when it holds none. Either
shape reads back the same, so a hand-written `room: kitchen` needs no
ceremony: >markdown

    ---
    room: kitchen
    tags: [java, streams]
    ---
<

A mention resolves to the concept it is the name of, else to the concept that
lists it as an alias. A mention nothing resolves to is undeclared — a state to
fix, never a reason to refuse a write. A tag that is never registered behaves
exactly as a plain label always has.

                                                     *memoria-concepts-attach*
|:MiaConceptAttach| puts a concept in one of the current engram's concept
fields — the concept counterpart of |:MiaSynapseAttach|. The engram decides
the brain. The field is picked when the brain has more than one, and the
concept from the ones that field takes (|memoria-concepts-types|). A name that
resolves is written under the concept's own name, so attaching an alias writes
the concept; a name already there changes nothing, and a field with
`list = false` gives up the value it held. The frontmatter line is rewritten
in place, every other line kept as it was.

                                                       *memoria-concepts-pick*
Choosing a concept is one interaction wherever it happens — attaching one, a
concept filename prefix, filling in meta, declaring an undeclared one: a
picker over the brain's concepts, those of the expected type first, with
`+ Create new concept` last. Creating asks for the name, the type, and then
each field the type's schema names.

                                                       *memoria-concepts-meta*
Filling in meta asks once per schema field, then once per key the concept
already carries that the schema does not name, so nothing is dropped by going
unasked. Each prompt is filled in with the current value: leave it to keep it,
clear it to remove the key. Anything else — aliases, notes, a rename — is an
edit to `mia_concepts.json` itself.

                                                 *memoria-concepts-undeclared*
|:MiaConceptFill| walks the undeclared concepts, most-used first. Each one is
either registered under its own name, or attached to a concept you pick as an
alias of it. No engram is touched either way.

The atlas reports concepts only once the registry holds something
(|memoria-atlas|): a brain that has declared nothing is not told that
everything it writes is undeclared. |:MiaConceptFill| is asked for, so it
answers regardless.

==============================================================================
8. ATLAS                                                   *memoria-atlas*

Each brain keeps a derived index in `.mia_atlas.json`: per engram its title,
synapses, linked engrams, concept fields (e.g. `tags`) and tasks, plus
backlinks, which engrams name each concept, and the registered concepts by
type. It can be deleted at any time.

A mention is indexed under the concept it resolves to (|memoria-concepts|),
so an engram writing an alias counts for the concept itself.

The atlas brings itself up to date whenever memoria reads it: new and changed
engrams are parsed again, deleted ones dropped. Edits made outside Neovim are
picked up the same way. An edit to `mia_concepts.json` is noticed too, and
re-derives what depends on it without parsing a single engram again.

|:MiaAtlasRebuild| builds it from scratch and puts what is wrong in the
quickfix list:

- a synapse or link to an engram that does not exist;
- a synapse whose inverse is missing on the other engram;
- frontmatter that cannot be read;
- a concept an engram names that nothing in the registry resolves to, at the
  concept field's line;
- a registered concept no engram names, at its key in `mia_concepts.json`.

The last two appear only once the registry holds a concept.

With `!` it first writes every missing inverse, and regenerates each existing
SYNAPSES block from config, adding lines for fields configured since. Neither
concept problem has a repair to write; |:MiaConceptFill| is what fixes an
undeclared one, and an orphan is deleted or kept by hand.

10. CLI                                                      *memoria-cli*

`bin/mia` is memoria with no editor running: the same functions the commands
call, from a shell. A script, a git hook, another editor, an AI agent — see
|memoria-cli-agents| for that one.

A brain is readable without memoria, being markdown and JSON. What is not
writable without it is a correct one: a hand-written engram misses its
generated header, and a hand-added synapse misses its inverse. >

    bin/mia <command> [--brain <name>] [args]
    bin/mia [command] --help
<
                                                        *memoria-cli-config*
It is a Lua script run by `nvim -l`, which skips the user's config, and with
it the `setup()` tier (|memoria-config|) — an engram written without that tier
would have the built-in fields and template, not yours. So the script loads
the config itself: `$MEMORIA_INIT`, else `stdpath("config")/init.lua`. A
config that does not call `setup()` is an error rather than a fall back to the
defaults, since that fallback is exactly the engram in the wrong shape; the
error names the likely causes (memoria lazy-loaded on a command or key,
md-drafting.nvim missing).

`MEMORIA_INIT=NONE` skips the config and sets memoria up with its defaults —
for tests, and for a machine with no config worth loading. The brain's
`.mia_dna.json` still applies on top. `nvim -l` loads no packages, so
md-drafting.nvim has to be on `package.path` already for that to work.

                                                        *memoria-cli-output*
One JSON object on stdout, and an exit status to match: >

    { "ok": true, "result": { "path": "/home/me/notes/work/20260801_x.md" } }
    { "ok": false, "error": "(work) engram 20260801_x.md already exists" }
<
`0` for `ok`, `1` otherwise. Errors name their brain the way prompts do.
Everything else — the config's own output, memoria's own diagnostics — goes to
stderr, so stdout is only ever the result.

`--help` is the one exception: it prints how to call the CLI as plain text,
since it is meant for a person reading it, and exits 0. `--help` after a
command explains that command and what each of its arguments is for. It loads
no config, so it still answers when nothing else does.

                                                      *memoria-cli-commands*
`bin/mia commands` prints the list below as JSON, with each command's
arguments, and is the place to start; `bin/mia --help` is the same list in
words. Brain-scoped commands take `--brain`, needed only when more than one
brain is registered (|memoria-brains|).

    brains                  Every brain: name, location, whether it exists
    engrams [--concept C]   Every engram: filename, title, concept fields
                            and when it changed; only those naming C, or
                            any of its aliases, when given
    engram {file}           One engram: its atlas entry, its backlinks and
                            its content
    concepts [--type T] [--undeclared]
                            Every registered concept with the engrams naming
                            it; only those of type T when given. With
                            --undeclared, the mentions nothing resolves to
                            instead, most-used first
    tasks [--state S]       The tasks, by state: "not_done", "done", or both
    check                   Rebuild the atlas and report what is wrong, each
                            with its file, line and kind
    rebuild [--fix]         The same; with --fix, repair what can be
                            repaired first
    create-engram --title T [--field name=value,...] [--body text|-]
               [--concept C] [--concept-field F]
                            Create an engram, opening nothing. --field once
                            per concept field; --body - reads stdin, so
                            multi-line prose needs no shell quoting;
                            --concept names the concept a brain with
                            `prefix = "concept"` prefixes it with, and
                            --concept-field which field it goes in when more
                            than one takes its type
    attach-synapse {source} {field} {target}
                            Link two engrams, writing the inverse on the
                            other one
    create-concept --name N --type T [--meta name=value]
                            Create a concept; --meta once per key. A name
                            already registered is an error
    edit-concept --name N [--type T] [--meta name=value]
                            Change a registered concept's type or meta,
                            key by key; `--meta name=` removes a key. A name
                            not registered is an error
    attach-concept {source} {field} {concept}
                            Put a concept in an engram's concept field. A
                            name nothing declares goes in as given
    commands                Every command and its arguments

The surface is reading and adding. `rename_engram` and `delete_engram` are not
on it: both reach beyond the file named, which is a change for someone to
confirm in the editor rather than for something unattended to do unasked.

                                                        *memoria-cli-agents*
An AI agent needs only to be told it exists. Point one at it from its
instructions file (`CLAUDE.md`, `AGENTS.md`): >

    Notes live in memoria brains — folders of markdown engrams. Never write
    or link one by hand: a hand-written engram misses its generated header,
    and a hand-added link misses its inverse.

    Use <path-to>/memoria.nvim/bin/mia. Start with `bin/mia commands`, which
    prints every command and its arguments as JSON. Each call prints one JSON
    object and exits 0 ("ok": true) or 1.
<
                                                       *memoria-cli-editing*
The CLI writes to disk, never to a buffer. An engram open in a running Neovim
is reloaded by 'autoread'/|:checktime| when unmodified; with unsaved changes
you get |W12| and decide which side wins. The atlas refreshes whenever either
side reads it, so each picks up what the other wrote.

11. API                                                      *memoria-api*

    local memoria = require("memoria")

    memoria.setup({opts})
        Check the dependency, store options, create commands. Returns true,
        or nil and why not.

Two layers. `memoria.{feature}` is what the |memoria-commands| call: it asks
for what you left out, opens what needs opening, and reports what went wrong —
bind these to a keymap. `memoria.core.{feature}` is the same feature without
any of that: it asks nothing, opens nothing, and answers a result, or nil and
an error naming no brain. The CLI (|memoria-cli|) calls only the second.

    memoria.brain.register({path}, {name})
        Register a folder as a brain, reporting the result.
    memoria.brain.deregister({name})
        Remove a brain from the registry; picked when not named.
    memoria.brain.switch({name})
        Set the active brain; picked when not named.
    memoria.brain.open_config({name})
        Open a brain's .mia_dna.json, creating "{}" when it has none.
    memoria.brain.print_list()
        Echo every brain, see |:MiaBrainList|.
    memoria.brain.pick({run})
        Pick a registered brain and pass it to {run}.
    memoria.brain.resolve({name}, {run})
        Resolve a brain (see |memoria-brains|) and pass it to {run}, with the
        picker as the last step.
    memoria.brain.choose({name}, {run})
        The picker straight away when {name} is empty, for choosing a brain
        rather than acting in one.

    memoria.engram.create_engram({brain}, {opts})
        Ask for a title, create the engram and open it at its cursor, asking
        again when the title cannot be a filename. With `prefix = "concept"`
        the concept is picked first.

    memoria.concept.create_concept({brain}, {name})
        Create a concept, asking for its name when {name} is not given,
        then its type and fields.
    memoria.concept.attach_concept({opts})
        Put a concept on the current engram. {opts}.source (path, default:
        the current buffer), {opts}.field and {opts}.concept are asked for
        when left out.
    memoria.concept.set_concept_meta({brain}, {name})
        Fill in a concept's meta; picked when {name} is not given.
    memoria.concept.find_undeclared_concepts({brain})
        Walk the undeclared concepts, see |memoria-concepts-undeclared|.
    memoria.concept.print_list({brain})
        Echo the concepts, see |:MiaConceptList|.
    memoria.concept.pick_or_create({brain}, {opts}, {run})
        Pick a concept or register one, and pass it to {run}. {brain} is a
        resolved brain; {opts} takes `prompt`, `name` (filled into the
        create prompt) and `concept_type` (all this field takes, and the
        type a new one is given). See |memoria-concepts-pick|.
    memoria.concept.pick_field({brain}, {fields}, {run})
        Pick which concept field to write in, and pass it to {run}.

    memoria.synapse.attach_synapse({opts})
        Link the current engram to another. {opts}.source (path, default: the
        current buffer), {opts}.field and {opts}.target are asked for when
        left out.

    memoria.atlas.rebuild_atlas({brain}, {opts})
        Rebuild and report into the quickfix list. {opts}.fix repairs missing
        inverses and backfills SYNAPSES blocks first.

Every function below answers a result, or nil and an error.

    memoria.core.brain.register({path}, {name})
        Register a folder as a brain. Returns the brain.
    memoria.core.brain.deregister({name})
        Remove a brain from the registry. Files are never touched.
    memoria.core.brain.switch({name})
        Set the active brain. Returns it.
    memoria.core.brain.resolve({name})
        The brain to act in, see |memoria-brains|. The picker is the view's,
        so an unnamed brain that resolves to nothing is an error here.
    memoria.core.brain.ensure_config({brain})
        A brain's .mia_dna.json, written as "{}" when it has none. Returns
        its path.
    memoria.core.brain.active()
        The active brain, or nil.
    memoria.core.brain.current()
        The brain commands would act on, and why, or nil.
    memoria.core.brain.containing({file})
        The brain whose folder holds {file}, or nil.
    memoria.core.brain.get({name})
        A registered brain, or nil.
    memoria.core.brain.list()
        Every brain, sorted by name.
    memoria.core.brain.names()
        Every brain name, sorted.

    memoria.core.engram.create_engram({brain}, {opts})
        Create an engram, opening nothing. {opts}.title is required,
        {opts}.fields fills the frontmatter, {opts}.body lands at %cursor%,
        {opts}.concept is the concept a "concept" prefix uses. Returns
        `{ path, cursor }`, or nil, an error, and a code: "empty_slug",
        "collision", "prefix" or "concept" (see |memoria-engrams|).
    memoria.core.engram.header({cfg}, {fields})
        The generated header for a config, with {fields}' values in it.
    memoria.core.engram.filename({cfg}, {slug}, {opts})
        The filename a slug gets under the configured prefix. {opts} takes
        `time` and `concept`.
    memoria.core.engram.slugify({title}, {separator})
        The filename-safe slug of a title.

    memoria.core.synapse.attach_synapse({opts})
        Link two engrams and refresh the atlas. {opts}.source (path),
        {opts}.field and {opts}.target are all required. Returns what it
        linked.
    memoria.core.synapse.connect({brain}, {source}, {target}, {field})
        Link two engrams by filename, both sides.
    memoria.core.synapse.locate({path})
        The brain and filename of an engram path, or why it is not one.

    memoria.core.atlas.refresh({brain}, {opts})
        Bring the brain's atlas up to date and return it. {opts}.full parses
        every engram again.
    memoria.core.atlas.rebuild_atlas({brain}, {opts})
        Rebuild from scratch and check it. Returns `{ atlas, problems }`;
        {opts}.fix repairs missing inverses and backfills SYNAPSES blocks
        first.
    memoria.core.atlas.locate_problems({brain}, {problems})
        The same problems, each with the file and row it sits on.
    memoria.core.atlas.check({atlas}, {cfg}, {registry})
        Everything wrong with a brain's links and concepts, each with a kind.
        Without {registry}, or with an empty one, no concept is reported.

    memoria.core.concept.list({brain})
        Every registered concept, sorted by name.
    memoria.core.concept.get({brain}, {name})
        A registered concept by its exact name.
    memoria.core.concept.resolve_concept({brain}, {mention})
        The concept a mention names, by name or alias.
    memoria.core.concept.create_concept({brain}, {name}, {type}, {fields})
        Create a concept. A name already registered is an error.
    memoria.core.concept.set_concept_meta({brain}, {name}, {type}, {fields})
        Write a concept's meta key by key, registering it when new ({type}
        is then required). An empty value removes its key.
    memoria.core.concept.add_alias({brain}, {name}, {alias})
        Have a concept answer to another name as well.
    memoria.core.concept.attach_concept({opts})
        Put a concept in an engram's concept field and refresh the atlas.
        {opts}.source (path), {opts}.field and {opts}.concept are required.
        Returns `{ brain, source, field, concept }`.
    memoria.core.concept.find_undeclared_concepts({brain})
        The mentions nothing resolves to, most-used first: `{ name, count,
        engrams }` each.
    memoria.core.concept.ensure_registry({brain})
        The brain's mia_concepts.json, written as "{}" when it has none.

A concept is `{ name, type, aliases, note, meta }`.

A brain is `{ name, location }`.
